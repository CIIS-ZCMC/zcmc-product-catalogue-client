# UNSPSC classification assistant

How the product form helps staff choose a UNSPSC commodity, and what the backend would need for it to work better.

## Data source

- The server seeds the `categories` table from `database/data/unspsc_categories.csv` (zcmc-product-catalogue-server), generated by `generate_unspsc_csv.py` from a UNGM `unspsc_english.xlsx` export. It has 158,520 rows across four levels (Segment 0, Family 1, Class 2, Commodity 3), most with an official definition.
- No UNSPSC version, release date or licence note is recorded in the CSV, the table or the API. The UI therefore shows "Version not recorded in the dataset" and stores nothing extra. Products keep what they already stored: `category_key` and `unspsc_code`.
- No mock data is used. Every code, title and definition shown comes from the server.

## What the client does

`src/services/unspsc-service.js` never loads the whole dataset:

1. The typed text (or the item name) is parsed by `parseQuery` in `src/lib/unspsc.js`. An all-digit query of 2 to 8 digits is a code lookup. Otherwise stop words, sizes, strengths and units are dropped, because UNSPSC titles do not contain them.
2. Up to three of the longest words are sent to `GET /categories/commodities?q=<word>&limit=60` in parallel. Each word is reduced to a LIKE-friendly stem (`batteries` → `batter`).
3. The candidates are merged and ranked by `rankCommodities`, using rules that each add a readable reason:
   - Exact code: 100. Code prefix (segment, family or class): 60.
   - Each query word found as a whole title word: 20. A word that only starts a longer title word: 12. The first word (the noun in ZCMC names): +10.
   - Every word in the title: +25 ("strong match"). Exact phrase: +15.
   - Words found only in the parent class, family or segment titles: +6 each. Words found only in the definition: +3 each.
   - Words negated with "non" ("Non-nitrile") do not count. Shorter titles win ties.
4. If the top two results have the same strength and nearly the same score, the UI asks the user to compare them before choosing.

Browsing uses `GET /categories/roots` and `GET /categories/:key/children`, one level at a time, cached for the page session. The selected commodity's hierarchy comes from `GET /categories/:key`.

The rules suggest; they do not decide. The user always selects a commodity explicitly, and can change or clear it.

## Known limits and backend work that would help

| Gap | Effect today | Suggested backend change |
| --- | --- | --- |
| `searchCommodities` matches one LIKE pattern on title, code or key, and returns rows in table order | Multi-word queries rely on client-side merging. A common word (e.g. "alcohol") can hit the 60-row cap before the best match, and the UI then says to add a more specific word | Match each word separately, search `definition` as well, and order by relevance (MySQL FULLTEXT or a scored query) |
| No keywords or synonyms in the dataset | "examination" only matches "exam" because of the abbreviation rule; true synonyms ("injector" for "syringe") never match | An approved synonym/keyword table maintained by the procurement unit, searched by the endpoint |
| No dataset version | Products cannot record which UNSPSC release they were classified against | Store the release (e.g. "UNSPSC v26.0801") in config or a `classification_sources` table, return it from the API and save it with each product |
| `/categories/commodities` returns level 3 only | Filtering the product list by a family or class must go through the UNSPSC Explorer | Optional `level` parameter (the `/categories/search` endpoint already supports one) |

## Optional AI or semantic matching (not implemented)

Semantic search (embeddings or an LLM) could rank "disposable syringe" closer to "Medical syringes" even without shared words. It is not included because it would:

- **Cost:** add per-request API fees or a self-hosted embedding service, plus storage for 158k vectors.
- **Privacy and security:** send product descriptions outside the hospital network unless self-hosted, which needs approval under the hospital's data rules.
- **Integration:** require a new server endpoint, a background job to embed the dataset, and monitoring for drift between releases.

If approved, it should stay a recommendation layer that feeds candidates into the same explainable ranking and explicit selection, never an automatic classification.
